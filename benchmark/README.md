# postgrejs Benchmarks

Compares postgrejs against `pg` (node-postgres) and `postgres` (postgres.js)
on the same Postgres server, the same machine, and the same workload. For the
methodology, disclosed asymmetries, and the latest generated numbers, see
[`../doc/BENCHMARKS.md`](../doc/BENCHMARKS.md) at the repo root — it is regenerated by
`npm run bench:report`, not hand-edited.

## Running

A Postgres server is required (the repo's own `docker-compose.yaml` works:
`docker compose up -d postgres`). Connection settings are read from the same
`PGHOST`/`PGPORT`/`PGUSER`/`PGPASSWORD`/`PGDATABASE` env vars used by the test
suite; the benchmark keeps its fixture data in its own `bench` schema
(override with `PGBENCHSCHEMA`), separate from the test suite's `test`
schema.

```bash
# Full default matrix: every scenario, every library, 3 repeats each
npm run bench

# Fast iteration while developing a scenario/adapter
npm run bench -- --scenario=simple-query-execute --lib=pg,postgrejs --repeats=1

# Regenerate BENCHMARKS.md from the latest benchmark/results/*.json
npm run bench:report
```

`--scenario=` and `--lib=` accept `all` (default) or a comma-separated
subset. Scenario names: `connect`, `simple-query-execute`,
`simple-query-execute-concurrent`, `mixed-types-decode`, `simple-query-fetch`,
`cursor-stream`, `pool-simple-query-execute`, `pool-extended-query-execute`,
`prepared-statement-reuse`.
Library ids: `postgrejs`, `pg`, `postgres`.

Each `(library, scenario)` pair runs in its own child process, spawned one at
a time — never in parallel — so CPU/connection contention on your machine
doesn't skew the numbers. Results land in `benchmark/results/*.json`
(gitignored raw data backing whatever `../doc/BENCHMARKS.md` currently reports).

## Rigor vs. speed

The default iteration/warmup/repeat counts are kept modest on purpose, so a
full `npm run bench` run finishes in a few minutes — this is a tool meant to
be run repeatedly during development, not just once. For numbers you intend
to publish or cite:

- Raise `--repeats` (e.g. `--repeats=10`) — the report uses the median across
  repeats, so more repeats means a more defensible median.
- Raise `BENCH_BULK_ROWS` (default `50000`) to seed and query more rows for
  the `cursor-stream` scenario: `BENCH_BULK_ROWS=500000 npm run bench`.
- Run on an otherwise-idle machine, with the Postgres server and the
  benchmark process on the same host to keep network variance out of the
  numbers (as the default setup already does).
- Per-scenario iteration/warmup/time budgets live in `benchmark/scenarios/*.ts`
  (the `bench` field of each `*_SCENARIO` export) if you want to raise them
  for a specific scenario rather than just repeating the whole matrix more.

## Adding a scenario or adapter

- Shared SQL text, row counts, and other constants for a scenario live in
  `benchmark/scenarios/<name>.ts`; register it in `benchmark/scenarios/index.ts`.
- Each library implements the scenario in its own adapter
  (`benchmark/adapters/<lib>.adapter.ts`) using whatever calling convention is
  idiomatic/fastest for that library — adapters are intentionally not forced
  through one shared low-level `query()` shape (see `../doc/BENCHMARKS.md`'s
  methodology section for why).
- `benchmark/adapters/registry.ts` is a dynamic-import map from library id to
  adapter module, so a new adapter (e.g. an opt-in `pg-native`) can be added
  without touching the default matrix.
